Escopo de turma num lugar só. Nenhum controller filtra turma à mão — tudo passa por um componente único. É o arquivo que se mudaria para suportar várias instituições.

O aviso da véspera é local. O servidor avisa o aparelho quando algo muda; o alarme é agendado no celular. Assim servidor dormindo não derruba a notificação.

Este slide tem três caixas e uma ideia: o celular não decide nada. A frase "entidade do banco nunca cruza o controller" merece explicação se perguntarem: a API sempre devolve um objeto de transporte, montado à mão. Isso é o que impede o hash da senha de vazar numa serialização automática — um erro clássico e silencioso. As duas caixas de baixo são as decisões de arquitetura que eu defenderia num Q&A: - Escopo de turma centralizado: se cada controller filtrasse à mão, bastava um esquecer. - Aviso local em vez de empurrado pelo servidor: o plano gratuito hiberna. Se o alarme dependesse de um job no servidor às 19h, ele simplesmente não dispararia — e o requisito falharia em silêncio, que é o pior tipo de falha. Se perguntarem "por que não Firebase, seria mais rápido": slide de recursos responde, mas a versão curta é que o modelo de dados tem relação muitos-para-muitos e histórico auditável, que é exatamente o que banco relacional faz bem e banco de documentos atrapalha.
